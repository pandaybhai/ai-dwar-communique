- Flows v2 runs live in flow_runs/flow_versions/flow_run_events and execute only via src/lib/flow-engine.server.ts (minute tick in flow-worker + webhook reply hook); legacy event flows keep flows/flow_steps/scheduled_sends — why: v2 must never change how existing store flows behave.
- Merchant-owned third-party accounts (Google, Razorpay for flows) live in workspace_connections with secrets only in Vault via service-role RPCs — why: secrets must never reach client-readable tables.
- Flows v2 HTTP-step header values live only in flow_http_secrets/Vault (bound to the step's scheme+host+path) and the graph keeps a secret_id; exports/imports carry header names only — why: flow_versions is readable by every member.
- Flow step names in the palette (NODE_META label/hint) are wording only; the stored NodeType keys (e.g. "carousel" = WhatsApp shop) and /app/catalog routes never change — why: saved flows and old links store those keys.
- campaigns.charged_amount mirrors the sum of the campaign's debit_message ledger rows, written only by syncCampaignCharged/settleCampaignSpend (re-read, raise-only) — why: Meta prices messages after settle, and the ledger is the single source of truth.
- Customer cards are opt-in per place (inbox Send card, Flows v2 "send_card" step, a campaign's attached card); every card goes through customer-cards.server.ts (sendCardToContact / sendCardOrFallback) and a failed card falls back to the plain photo/text. Aiden's and Show products' product card follows organizations.branding.product_cards_in_answers (only an explicit false turns it off) — why: a card must never block a message, and the default must equal pre-switch behaviour.
- AI backup providers (the Anthropic/OpenAI keys under /admin/ai Platform providers in Vault, else ANTHROPIC_API_KEY / OPENAI_API_KEY; Anthropic model = ANTHROPIC_BACKUP_MODEL, else platform_settings.ai_backup_anthropic_model, else claude-sonnet-5-5) are used only from src/lib/ai-fallback.server.ts via executeRun/embedTexts, read only after a primary outage (402/credit 403/429/5xx/unreachable), never for a workspace on its own (BYOA) key; embeddings fall back only to OpenAI text-embedding-3-small — why: no backup key must mean behaviour exactly as before, a healthy run must make no extra reads, and stored vectors only match the same embedding model.
- Customer card pictures are reused by cacheKey (org + kind + hash of vars incl. brand paint): memory, then the stored file in storage, render-card only on a miss; each real render (never a reuse) is recorded on ai_usage as card_render / card_preview through the service client and never charged — why: pricing is pending, ai_usage is read-only to members, and a restart must not redraw identical cards.
- src/lib/batch10c-replay.test.ts replays every live published flow graph (test-support/live-flows) through validateGraph, the simulator and the engine against a baseline recorded on main; a deliberate behaviour change must be listed in its ALLOWED with the reason — why: no existing flow may change behaviour silently.
- Flows v2 publish goes only through publishFlowVersion (src/lib/flow-publish.server.ts): one transaction via flow_publish_version once supabase/aidwar-migrations/20261015_flow_publish_atomic.sql is applied, step by step with rollback until then — why: never a half-published version or a published flow left switched off.
- Extending a trial goes only through extendTrial (billing.server.ts, admin action extend_trial): it moves organizations.trial_ends_at and nothing else — never assignPlan or a feature re-sync; and a trial workspace's auto-pay mandate starts at trial_ends_at (firstChargeAt in subscriptions.server.ts) — why: more trial days must never change features, and paying early must not cost the remaining trial days.
- The website reader never takes products from legal/policy pages or numbered clause headings (isLegalPage / looksLikeLegalClause in product-extract.server.ts) — why: a terms page's "7. Limitation of liability … ₹5,000" was saved as a product.
- Website reads (full read, refresh, backfill) run only through crawlWebsite in knowledge.server.ts in bounded runs: ≤25 pages, no new page after ~60 s, nothing past ~85 s or the worker's deadlineAt; every page is saved by savePage the moment it is read (document, chunks, product, knowledge_urls row); own fetch first, paid readers only for pages under 300 chars; a read stuck in "syncing" resumes via resetStaleReads with pages_done kept — why: pg_net drops the worker call at 120 s, and a whole read held in memory was lost every time (myzoori.com, 6 Oct). The Day-0 read stays one pass of day0_page_limit pages in the Reading tab's engine order.
- Every page address goes through canonicalPageUrl (site-urls.ts): www/no-www, http/https, trailing slash, fragments, tracking and listing/filter params are one address on the source's own origin, and the source follows its homepage redirect (config.url updated, previous_origins kept) — why: myzoori.com → www.myzoori.com read as two sites.
- Deleting a website source is soft only (softDeleteWebsiteSource: status disabled + config.deleted_at, its crawl products hidden by id); restoreWebsiteSource undoes it exactly and purgeDeletedSources (nightly, knowledge-backfill) removes it after 7 days — why: a deleted source must be restorable, and retrieval already skips disabled sources.
- Campaign messages are sent only by runCampaignDispatch (src/lib/campaign-dispatch.server.ts) from /api/internal/campaign-worker: claim a few recipients at a time (claim_campaign_recipients), put back what a live run didn't send, and settle 'sending' rows older than CAMPAIGN_STALE_MS from what was recorded (a messages row with metadata.campaign_recipient_id = sent, none = failed, never re-sent); Meta's throughput errors (130429 etc.) are retried, a send with no answer never is — why: each recipient must get a campaign message at most once, even when runs overlap or die.
- Lanes split phone numbers (laneShare) and a number's speed CAMPAIGN_NUMBER_MPS is divided across the lanes that send for it; only lane 0 starts campaigns, holds credits and settles dead runs — why: all lanes together must stay under Meta's per-number throughput, and a hold must exist before the first message.
- A status webhook moves a message with one conditional update (never .or() on a mutation: PostgREST re-applies it to the returned rows) and its campaign recipient through campaign_recipient_status() (or two conditional updates before 20261016_send_at_scale.sql), found by the biz_opaque_callback_data recipient id when Meta echoes it — why: ~3 statuses arrive per message, each must be counted once, and a status may arrive before the sender's batched row write.
